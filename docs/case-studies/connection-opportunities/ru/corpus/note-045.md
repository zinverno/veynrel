# Памятка по эксплуатации сервиса миниатюр

## Обычное развёртывание

Сервис миниатюр забирает ожидающие задания, создаёт временные изображения и публикует готовые файлы переименованием. Новую версию сначала запускают на одном пробном обработчике — canary worker. Перед обновлением остальных обработчиков сравнивают время ожидания в очереди, частоту ошибок и контрольные суммы результатов. Конфигурация читается при запуске, а работающая ревизия отображается в выводе состояния. Если сохранить предыдущий исполняемый файл, откатить версию будет проще. Но откат кода не отменит уже опубликованные результаты.

## Кто владеет заданием

Планировщик выдаёт обработчикам временное право на задание — lease. Если процесс бросил работу, после истечения этого срока задание сможет забрать другой процесс. Пока работа идёт, сигналы heartbeat продлевают срок. На панели мониторинга видны текущий владелец и время истечения lease. Зависший процесс может продолжить работу после долгой паузы, хотя его представление о владении уже устарело. Показания часов помогают разбирать инцидент, но сами по себе не дают права публиковать результат. При разборе такого случая нужно сохранять исходные идентификаторы заданий.

## Плановое обслуживание

При штатном завершении остановите приём заданий, дайте коротким задачам закончиться и сохраните идентификаторы незавершённой работы. Отметьте окно обслуживания в журнале событий. После потери машины в очереди могут остаться записи об истёкших правах на задания. Если удалить очередь, исчезнут и сведения, по которым можно понять, какие задания завершились. Новый планировщик должен читать надёжно сохранённое состояние, а не доверять счётчику в памяти старого процесса.

## Защита от записи прежнего владельца

При каждой новой выдаче права на задание назначается монотонно возрастающий номер — fencing token. Хранилище запоминает наибольший номер, принятый для ресурса, и отклоняет записи с меньшим номером. Одного истечения lease недостаточно: прежний владелец может выйти из паузы и попытаться опубликовать результат уже после передачи задания другому процессу. Поэтому проверять номер должен сам ресурс, принимающий результат. Проверка номера и запись результата должны быть атомарными. Проверки времени последнего heartbeat только внутри обработчика недостаточно.

Последовательность номеров должна сохраняться при перезапуске планировщика. Повторное использование старого номера позволило бы запоздалой записи выглядеть актуальной. Отказы при проверке fencing token нужно показывать как события от устаревшего обработчика, а не повторять запись, считая отказ временной ошибкой хранилища. Это правило определяет право процесса на запись, а не устраняет дубликаты одинаковых байтов изображения.

## Разбор инцидента

Соберите идентификатор задания, историю lease, принятый fencing token и ревизию результата. Сопоставьте события по времени, не предполагая, что порядок поступления записей в журнал совпадает с порядком самих событий: во время паузы процесс мог накапливать записи в буфере. Исправление можно считать завершённым, только когда принимающий ресурс не допускает публикации от прежнего владельца, а пробный прогон подтверждает отказ по старому праву на задание.
