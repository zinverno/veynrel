# Lease истёк, а воркер вернулся

Сценарий для очереди тяжёлых расчётов. Воркер A забрал задание и завис. Heartbeat пропал, lease истёк, планировщик отдал задание воркеру B. B закончил работу. Потом A ожил и тоже пытается опубликовать результат.

В интерфейсе давно показан новый владелец. Старый процесс об этом может ничего не знать. Истечение времени не останавливает его физически.

## Где проверять право на запись

Вариант — выдавать каждому новому владельцу монотонно растущий fencing token. Хранилище запоминает наибольший принятый номер для ресурса и отказывает записям со старым номером. Проверка и запись результата должны быть одной атомарной операцией. Если проверяет только воркер, остаётся та же проблема с паузой.

После перезапуска планировщика номера не должны начинаться заново. Отказ по старому номеру стоит показывать отдельно: бессмысленно повторять его как временную ошибку диска. Одинаковое содержимое результатов тут ничего не меняет — проверяется право писать.

Для такого варианта fencing есть тонкость: одного факта выдачи нового номера мало. Хранилище должно узнать его. В сценарии выше оно уже приняло запись B и поэтому отклонит A. Поведение до первой записи B надо определить отдельно в протоколе передачи владения.

## Рядом с выкладкой

Новую версию сначала пустить на один canary worker. Сравнить время ожидания в очереди, ошибки и контрольные суммы выходных файлов. Конфиг читается при старте, ревизия видна в статусе. Готовые локальные файлы публикуются переименованием временных. Старый бинарник оставить для отката, но уже опубликованные эффекты откат кода не отменит.

На остановке: закрыть приём заданий, дать коротким закончиться, сохранить ID остальных и отметить обслуживание в журнале. Очередь с истёкшими lease не чистить вслепую — там сведения о выполненной работе. Новый планировщик читает сохранённое состояние, а не старый счётчик из памяти.

## Что ещё проверить

Нужен прогон с паузой A и записью B. В журнал собрать ID задания, историю lease, принятый номер и ревизию результата. Записи могут прийти не по порядку: зависший процесс мог буферизовать лог. Часы и панель владельцев помогают разбору, но не доказывают право на запись.

Этот сценарий пока не запускался. Критерий проверки — старую запись действительно отклоняет принимающее хранилище.
